## Why this matters

The repository currently has a coherent SpecKit feature for a narrow PR-review
spike, but its data model only represents CodeRabbit, gito and pr-agent.
Coding agents, seeded defects, resource constraints and a dashboard need shared
language before schemas or UI are built. Without this contract, every adapter
will invent incompatible definitions for a run, success, cost and score.

This plan produces an approved, technology-neutral product contract and makes
future work traceable in separate SpecKit features. It does not build the
database, workers, frontend or benchmark corpus.

## Steps

### Step 1: Establish the bounded SpecKit feature

Run the feature-creation command above. If a `002-*` feature or branch already
exists, inspect it and reconcile rather than overwriting it. Update `CLAUDE.md`
only after the new specification has passed its checklist.

Before feature implementation, turn the current placeholder SpecKit constitution
into the project's real governance document. Propose these principles for
operator approval: reproducible versioned inputs; ground truth independent of
candidate claims; attempt provenance and immutable artifacts; equal/sandboxed
candidate conditions; resource-aware serial local inference; and protected
hidden evaluation data. Each principle needs a measurable enforcement hook in
the later plans. Do not ratify a constitution on behalf of the operator.

Write `spec.md` for the platform, with independent user stories for:

1. an evaluator selecting a versioned review/coding suite and candidates;
2. an operator queuing a run under one local-GPU slot;
3. an evaluator comparing attempts with provenance and uncertainty visible;
4. a curator creating a task or review fixture without exposing hidden truth.

Require immutable attempts, worktree isolation, artifact retention, retry and
cancel semantics, and an auditable weighted-ranking policy. Explicitly state
that historical CodeRabbit comparisons are observational, not quality truth.

**Verify**: `rg -n '^### User Story|FR-|SC-' specs/002-benchmark-platform/spec.md` shows all four stories, functional requirements and measurable criteria.
Also verify `rg -n '\[PRINCIPLE_|\[PROJECT_NAME\]|\[.*_DESCRIPTION\]' .specify/memory/constitution.md` returns no placeholder tokens after ratification.

### Step 2: Decide and document the domain contracts

Create `data-model.md` and JSON/OpenAPI-facing contracts which distinguish the
following stable nouns. Do not reuse `Finding` as a universal run result.

| Noun | Minimum purpose / immutable identity |
|---|---|
| `BenchmarkSuite` / `SuiteVersion` | Review or coding suite, semantic version plus content digest |
| `BenchmarkItem` | One review fixture or coding task, visibility partition and source revision |
| `Candidate` / `CandidateVersion` | Model plus harness/tool and exact package/image version |
| `ExecutionPlan` | Frozen matrix, budgets, policy version, candidate/item selections |
| `Attempt` | One candidate × item sample, UUID, status and timing boundaries |
| `ResourceProfile` / `ResourceLease` | Named capacity class such as `local-94gb-gpu`, lease holder and expiry |
| `Artifact` | Content-addressed log, raw output, patch, test result or manifest with retention class |
| `Evaluation` / `Score` | Versioned evaluator output, metrics, confidence interval and score-policy reference |
| `DefectLabel` | Hidden review truth: ID, severity, taxonomy, impact, reproducer and scope |

Define status transitions with terminal states (`succeeded`, `failed`,
`timed_out`, `cancelled`, `invalid`) and a `queued → leased → preparing →
running → evaluating` path. State precisely which fields are public to runners,
operators and dashboard viewers. Describe artifact redaction and retention.

**Verify**: `rg -n 'Attempt|ResourceLease|DefectLabel|Artifact|queued|invalid' specs/002-benchmark-platform/data-model.md` finds every required concept.

### Step 3: Freeze measurement and fairness rules

In `research.md` record the observed constraints from the previous spike and
current official tool probes, each with date, command/version and source URL.
Make the following product decisions explicit in an ADR:

- review ranking uses human-approved seeded labels for precision, recall,
  severity-weighted recall, F1, duplicate rate, false-positive rate and
  completion rate;
- coding ranking uses hidden acceptance/regression tests first, then separately
  reports patch hygiene and optional human review;
- every local model/tool/item cell has at least three independent attempts;
- an excluded warm-up occurs per candidate version; order is randomized or
  counterbalanced and local inference capacity is one;
- report queue wait, setup, inference/agent wall time, evaluation time, token
  counts if available and cost estimate separately;
- show confidence intervals and a Pareto view; a total rank requires a named,
  versioned score policy with disclosed weights;
- use a blinded two-reviewer adjudication process for seeded findings and record
  agreement/disagreement.

**Verify**: `rg -n 'CodeRabbit|three|warm-up|queue wait|Pareto|adjudication|weighted' specs/002-benchmark-platform/{spec.md,research.md} docs/adr/*.md` returns each rule.

### Step 4: Define the implementation slices, not implementation details

Write `plan.md` and `tasks.md` so Plans 002–005 map to discrete SpecKit

Include acceptance gates for every slice and a clear migration boundary:

must not be silently converted into ranking attempts.

## Maintenance notes

Treat every schema and score-policy change as versioned. Never compare scores
across suite, evaluator or policy versions without showing the version boundary.
The domain names in this plan are API contracts: future adapters may add
metadata, but should not create competing meanings for `Attempt` or `Score`.
